# Checklist penyelesaian backend sampai production

**Kesiapan production yang sudah terbukti: 15% (7 dari 47 gerbang).**
**Sisa: 40 gerbang.** Diperbarui 4 Oktober 2026 (Asia/Jakarta).

## Cara membaca persentase

Angka ini mengukur gerbang penerimaan production yang sudah punya bukti, bukan banyaknya file/kode yang sudah dibuat atau perkiraan jam kerja. Satu gerbang bernilai sama; persentase = jumlah kotak `[x]` dibagi 47, dibulatkan ke persen terdekat. Gerbang alur fitur baru boleh dicentang setelah acceptance di dokumen terkait dan pengujiannya selesai. Smoke test atau unit test tidak dianggap sebagai bukti end-to-end. Angka akan dihitung ulang setiap kotak berubah. Audit seluruh 31 Markdown di `docs/` selesai; temuan yang butuh perbaikan/sinkronisasi tetap terbuka pada gerbang terkait. Pemeriksaan penuh pernah lulus pada revisi workspace sebelumnya, tetapi perubahan lokal terbaru belum lolos ulang seluruh `npm run check`; karena itu G-03 sementara tidak dihitung selesai. Tes terarah terbaru dicatat pada gerbang/perbaikan terkait.

**Status saat ini:** ada kode dan automated tests untuk banyak fitur; beberapa smoke/health/route check production juga pernah lulus. Namun, banyak jalur inti belum diuji dari awal sampai akhir dengan identitas pengguna dan bukti yang benar. Karena itu angka 15% adalah gerbang kesiapan rilis yang terbukti, bukan klaim bahwa hanya 15% kodenya sudah ada.

## Perbaikan lokal yang sudah dilakukan

Kotak di bagian ini mencatat perbaikan kode dan tes fokus. Ini **tidak** dihitung sebagai gerbang production, karena tesnya belum mencakup alur nyata dengan database/provider/user production.

- [x] Vision ML sekarang menerapkan batas waktu sampai body JSON selesai dan menolak nilai confidence kosong/tidak finite/di luar 0–1. Suite worker fokus lulus **61/61**.
- [x] Perubahan status kegiatan tidak mengirim pemberitahuan perubahan kepada anggota yang sudah batal; pembatalan memberi kabar kepada peserta aktif saat dibatalkan dan koordinator. Tes layanan kegiatan lulus **3/3** memakai SQL mock.
- [x] Pencabutan consent Instagram menjaga operasi retract `failed`/`needs_action` untuk pemulihan eksplisit dan tidak membuat post seolah aman terhapus. Tes regression lulus **4/4** memakai SQL mock.
- [x] Pemilihan media draft Instagram kini mencocokkan tipe dan ID subjek sehingga aset kejadian lain tidak terselip. Tes selector lulus **2/2**.
- [x] Login MFA: percobaan TOTP valid ke-5 sebelumnya tertolak karena batas SQL memakai `< 5` setelah nomor percobaan dinaikkan. Batas transaksi diperbaiki dan regression suite MFA lulus **12/12**; ini belum menggantikan tes PostgreSQL nyata atau E2E login.
- [x] OTP/reset password: penerbitan challenge per email+tujuan kini diserialisasi dan reuse cooldown atomik; percobaan salah dibatasi di SQL; reset password, konsumsi OTP, dan pencabutan sesi dikelompokkan satu transaksi; ganti password memastikan sesi peminta masih aktif lalu mencabut sesi lain dalam transaksi. Typecheck API dan tes API lulus **194/194**. Ini bukti level kode/mocks, belum tes concurrency/rollback PostgreSQL nyata; pengiriman Resend masih inline tanpa outbox/retry.
- [ ] Pemulihan scan antrean: perubahan kuota/idempotency lokal sudah dibuat; durable outbox, lease, fencing, dan tes Postgres/Redis belum tersedia. Batas re-run bila worker crash dan kode hasil terminal perlu diputuskan dari kontrak sebelum implementasi.

- [ ] **G-24 — SAPA R3/R4:** dokumen berbeda pendapat apakah domain read-only tools tersedia; source SAPA saat ini menyediakan tools baca, sedangkan policy pilot/izin belum dibuktikan. Selaraskan kontrak, dokumen, allowlist dan akses data; tool action tetap memerlukan persetujuan manusia. Buktikan pembatasan, audit, dan kill switch bila fitur ini masuk scope rilis.
- [ ] **G-25 — SAPA R5:** batas biaya, durasi, kuota, retry, health/provider degradation, retention, dan metrik teruji serta terlihat operator. Rate counter Redis kini menaikkan hitungan dan memasang TTL dalam satu Lua script; tes Redis nyata membuktikan 100 increment paralel, TTL non-sliding, dan perbaikan key legacy. Serialisasi turn per conversation/deduplikasi retry masih ditangani terpisah dan belum terbukti; provider/error/cost/replay/operasional juga masih terbuka.
- [ ] **G-26 — Alur akun lengkap:** gabungkan ACCOUNT-R1–R4 melalui UI/API memakai sesi nyata; semua aksi pengguna dan admin serta invalidasi cache/session lolos.

### Komunitas, relawan, dan dampak

- [ ] **G-27 — Dukungan/follow:** desired-state idempotent, unfollow, canonical merge, akses/kuota dan tanpa poin/risk side effect terbukti pada alur user.
- [ ] **G-28 — Pembaruan kondisi:** kirim teks/foto, revisi, visibility pending/public, koreksi, duplikasi pending, dan hak pemilik diuji end-to-end.
- [ ] **G-29 — Review manusia:** laporan, update, hasil kegiatan, Hermes run, approve/reject/request-evidence, retry, snapshot usang dan fallback manual tersambung end-to-end.
- [ ] **G-30 — Proyeksi publik dan peta:** private GPS/media tidak bocor; status/canonical/withdrawal memperbarui daftar, detail, timeline, tile/snapshot dan cache dengan konsisten.
- [ ] **G-31 — Siklus kegiatan:** admin membuat kegiatan, koordinator ditugaskan lalu menerima, publish/edit/jadwal/cancel/close dan scope izin koordinator diuji; alasan pembatalan yang aman terlihat pada halaman publik/peserta, sedangkan catatan internal tetap privat.
- [ ] **G-32 — Keanggotaan dan kapasitas:** join/cancel/deadline/waitlist serta dua pendaftar bersamaan diuji memakai transaksi PostgreSQL nyata. Tes kapasitas yang ada baru membuktikan urutan SQL lewat mock, belum membuktikan konkurensi DB.
- [ ] **G-33 — Kehadiran dan hasil:** attendance aktual, bukti before/after, hasil partial/complete, revisi dan review admin diuji dengan role yang tepat.
- [ ] **G-34 — Resolusi dari bukti:** klaim bukti immutable terikat laporan/revisi, partial tidak menyelesaikan laporan, revocation memicu review, points/timeline/audit/outbox konsisten.
- [ ] **G-35 — Dampak:** jumlah canonical, pengukuran per batch/tahap, coverage, null-vs-zero, deduplikasi dan koreksi dibuktikan dengan kasus hitung ganda. Definisikan apakah `verifiedKg` boleh menjumlahkan pengukuran sumber publik tanpa hasil kegiatan yang sudah disetujui; DTO menyebut `approved_public_sources`, sedangkan jumlah kegiatan/coverage memakai hasil approved. Buat fixture nyata untuk batch fisik multi-tahap, superseding, zero-vs-missing, result pending/approved, withdrawal/private dan hitung expected totals sebelum klaim metodologi.
- [ ] **G-36 — Notifikasi:** penerima yang berhak, status cancelled, deduplikasi, unread, tautan aman dan penarikan akses diuji. Perbaikan lokal untuk penerima cancellation/change sudah dibuat; tes fokus memakai SQL mock, jadi belum membuktikan transaksi PostgreSQL dan alur pengguna.
- [ ] **G-47 — Lifecycle laporan baseline:** buat/edit laporan, keputusan admin verify/reject/duplicate dan canonical merge, timeline, poin/badge/streak/leaderboard, batas harian, replay, reversal, dan sinkronisasi proyeksi diuji end-to-end tanpa efek ganda.

### Hermes review

- [ ] **G-37 — SAP ↔ Hermes E2E:** laporan masuk → intent/outbox → worker → Hermes/9Router → validasi snapshot/evidence → `review_runs` tersimpan → moderator melihat saran; tes kasus valid/stale/invalid/timeout/retry.
- [ ] **G-38 — Isolasi dan human fallback:** Hermes tidak punya tool/credential aksi, tidak membaca konteks pengguna lain, tidak mengubah keputusan; saat mati/kuota habis laporan tetap bisa direview manual.
- [ ] **G-39 — Evaluasi Hermes:** benchmark terukur untuk ketepatan bukti/status, hallucination, moderator time, latency dan cost; threshold dan versi model/prompt tercatat.

### Instagram

- [ ] **G-40 — Izin media dan rendition:** persetujuan pemilik + reviewer per channel/revisi; derivative yang benar-benar ter-render digunakan; original private tidak pernah menjadi public URL.
- [ ] **G-41 — Sumber draft sesuai kontrak:** report/update/result yang eligible dipetakan dengan benar, termasuk initial/resolution, approval invalidation, replacement, dedup dan lineage. Kontrak saat ini lebih luas daripada implementasi initial draft yang hanya mengambil report; kebijakan sumber harus disamakan dan diuji.
- [ ] **G-42 — Render poster:** foto bukti yang diizinkan, peta lokasi yang benar, dan judul/kategori yang sesuai sumber approved menurut `INSTAGRAM_POST_DESIGN.md`; lakukan pemeriksaan visual pada output final dan validasi metadata/format Instagram.
- [ ] **G-43 — Draft:** item berizin menghasilkan draft pada akun yang benar, caption/alt text dan revision snapshot tepat, alasan tidak eligible jelas, tanpa mengambil foto privat.
- [ ] **G-44 — Publish uji:** satu post sementara berlabel uji memakai aset yang izinnya tercatat; approval valid, provider menerima, status/ID/waktu konfirmasi tersimpan, reload/retry tidak menggandakan post.
- [ ] **G-45 — Retract dan rekonsiliasi:** hapus post uji setelah publish; verifikasi hasil hapus dari Meta. Uji timeout, publish-vs-withdraw race, delete yang gagal/404, disconnect dan restore tanpa menganggap gagal sebagai sukses. Pencabutan consent saat retract lama berstatus `needs_action`/`failed` harus meninggalkan post dan job pada status yang bisa dipulihkan, bukan `retracting` tanpa antrean.
- [ ] **G-46 — Callback Meta:** verifikasi pengaturan Deauthorize Callback dan Data Deletion Request URL memakai endpoint backend yang benar-benar ada, tervalidasi, dan tercatat; atau dokumentasikan bukti Meta tidak mewajibkannya untuk konfigurasi aplikasi ini.

## Urutan kerja berikutnya

1. Selesaikan audit semua dokumen dan kunci daftar acceptance/konflik di bagian atas checklist.
2. Perbaiki temuan konkret berisiko tinggi: pemulihan scan queue, parsing/timeout ML, erasure tombstone saat restore, notifikasi anggota cancelled, dan mismatch adapter Instagram.
3. Tambahkan integration tests dengan Postgres/Redis/Gradio/Hermes yang benar untuk perilaku concurrency, recovery, review persistence, dan scan lifecycle.
4. Jalankan tes yang dapat dibuktikan lokal; catat output/commit dan perbarui [laporan pengujian production](PRODUCTION_BACKEND_TEST_REPORT_2026-10-04.md).
5. Jalankan acceptance yang diizinkan di production dengan identitas dan aset test yang sah; jangan memasukkan data sintetis seolah-olah insiden nyata.
6. Selesaikan review deployment/restore/monitoring lalu hitung ulang persentase. Jangan menyebut 100% sebelum semua gerbang yang berlaku lulus.
